# Notes

The workflow has two stages. `ingest.py` normalizes each source into JSONL chunks and attaches provenance. PDFs become one chunk per physical page; CSV rows become individual chunks; and every non-empty XLS row is preserved, including title and narrative cells. `query.py` vectorizes the chunk text with TF-IDF over unigrams and bigrams, ranks chunks for a question, and returns source metadata with the evidence. A small year match boost helps prevent a matching scheme in the wrong Delhi annual statement outranking the requested year. Evaluation answers were then written only after checking the retrieved source row/page, with units retained or explicitly converted from thousands to crore.

The main limitation is table interpretation. Plain-text PDF extraction flattens multi-column tables, so numeric values still require interpreting the nearby table header. Hindi extraction is another limitation: the bilingual PDFs contain an English parallel line, but much Hindi appears as legacy-font text. The query normalizer repairs the supplied mojibake where possible and expands common Hindi scheme names into their English labels. A production version would add OCR/language-aware extraction, structural table parsing, hybrid dense retrieval, and a constrained generator that quotes the supporting values before producing an answer. I would also add automated development-set scoring and unit-aware tests.

One misleading automated signal I caught was an initial broad keyword search returning “Mahila Samridhi Yojana” from Delhi's 2026-27 statement while investigating the Odisha question. The text match was real but the jurisdiction and year were wrong. I checked the Odisha document directly and marked that evaluation item unanswered. This is why filename/year filtering and provenance review matter more than a high retrieval score alone for repetitive government budget tables.
